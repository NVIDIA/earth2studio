# NNJA-AI benchmark results

Generated by `nnja_ai_benchmark.py`. Analysis time `2024-01-01T00:00`,
tolerance `±30min`. Sandbox network to both the NNJA S3 mirror and the
nnja-ai GCS mirror was slow and highly variable in the environment this was
run in (single fetches sometimes took minutes even for small responses), so
treat absolute seconds as indicative, not authoritative -- rerun in your own
environment for a production comparison. Relative ordering (which source is
faster) was consistent across repeated runs.

## Satellite (amsua, mhs) -- like-for-like, same NNJA archive

| source | variable | seconds | rows | rows/sec |
|---|---|---|---|---|
| NNJAObsSat (raw BUFR, before) | amsua | 60.51 | 844,949 | 13,965 |
| NNJAAIObsSat (nnja-ai Parquet, after) | amsua | 30.35 | 424,751 | 13,995 |
| NNJAObsSat (raw BUFR, before) | mhs | 133.04 | 1,800,322 | 13,532 |
| NNJAAIObsSat (nnja-ai Parquet, after) | mhs | 108.40 | 898,623 | 8,290 |

**Caveat:** the nnja-ai path returned roughly half the footprint rows of the
raw-BUFR path for both sensors, despite both sources being asked for the
exact same sensor/time window against the same underlying archive. Per-row
throughput is comparable, and wall-clock is meaningfully lower for the
nnja-ai path (~2x for amsua, ~1.2x for mhs), but the row-count gap is
unexplained and needs follow-up before treating the two as strictly
equivalent -- it was not something this session had budget to chase down.
Possible causes to investigate: differing satellite/platform coverage
between the raw cycle file and the nnja-ai partition window, or a duplicate
message issue in one of the two decode paths.

## Conventional (t) -- NOT like-for-like

| source | variable | seconds | rows | rows/sec |
|---|---|---|---|---|
| NNJAObsConv (merged PrepBUFR, before) | t | 442.48 | 65,951 | 149 |
| NNJAAIObsConv (raw ADPUPA Parquet, after) | t | 15.51 | 5,523 | 356 |

`NNJAObsConv` reads NCEP's merged, QC'd PrepBUFR product, which folds
together multiple raw report families (rawinsonde, aircraft, profilers,
etc.) into one high-report-type-fidelity `t` population. `NNJAAIObsConv`
reads only the raw ADPUPA (rawinsonde) dump stream -- the nnja-ai catalog
does not currently publish the merged PrepBUFR product or a GPS-RO dataset.
The ~28x wall-clock speedup is real (no BUFR parsing, no PrepBUFR-scale
message volume), but the ~12x fewer rows reflects reading a narrower raw
data product, not equivalent coverage decoded faster. `NNJAAIObsConv` is a
reasonable option when raw radiosonde temperature/wind/derived-humidity and
raw surface pressure are enough; it is not a full substitute for
`NNJAObsConv`'s merged-PrepBUFR `t`/`u`/`v`/`q`/`pres`/`gps` coverage.
