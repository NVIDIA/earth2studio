# NNJA-AI benchmark results

Generated by `nnja_ai_benchmark.py`. Analysis time `2024-01-01T00:00`,
tolerance `±30min`. Sandbox network to both the NNJA S3 mirror and the
nnja-ai GCS mirror was slow and variable in the environment this was run in,
so treat absolute seconds as indicative, not authoritative -- rerun in your
own environment for a production comparison. Relative ordering (which source
is faster) was consistent across repeated runs.

## Satellite (amsua, mhs) -- like-for-like, same NNJA archive

| source | variable | seconds | rows | rows/sec |
|---|---|---|---|---|
| NNJAObsSat (raw BUFR, before) | amsua | 21.72 | 844,949 | 38,896 |
| NNJAAIObsSat (nnja-ai Parquet, after) | amsua | 18.91 | 844,949 | 44,691 |
| NNJAObsSat (raw BUFR, before) | mhs | 73.20 | 1,800,322 | 24,594 |
| NNJAAIObsSat (nnja-ai Parquet, after) | mhs | 61.19 | 1,800,322 | 29,422 |

Row counts now match **exactly** between the two paths (verified per
satellite, not just totals). An earlier run of this benchmark showed the
nnja-ai path returning almost exactly half the rows of the raw-BUFR path for
both sensors; that was a real bug in `NNJAAIObsSat`/`NNJAAIObsConv`
(`_manifest_slice_start` in `earth2studio/data/nnja_ai.py`), not a data
difference. The nnja-ai catalog's manifest indexes one row per UTC calendar
day at midnight, and `NNJADataset.sel(time=slice(tmin, tmax))` does a plain
`DataFrame.loc` slice against that index -- passing the true, sub-day `tmin`
(e.g. 23:30 the day before a 00:00 analysis time, from a symmetric
`time_tolerance`) silently dropped the entire previous-day partition file,
because its index key (previous midnight) sorted before `tmin`. Flooring the
slice start to midnight fixed it; see the module docstring for
`_manifest_slice_start` and the regression test
`test_nnja_ai_manifest_slice_start_floors_to_midnight`.

With that fixed, the nnja-ai path is a modest, genuine win here: ~1.15x for
amsua, ~1.2x for mhs, on equal row counts. Not the ~2x headline from the
buggy run -- most of the earlier "speedup" was an artifact of fetching half
the data.

## Conventional (t) -- NOT like-for-like

| source | variable | seconds | rows | rows/sec |
|---|---|---|---|---|
| NNJAObsConv (merged PrepBUFR, before) | t | 127.24 | 65,951 | 518 |
| NNJAAIObsConv (raw ADPUPA Parquet, after) | t | 6.29 | 5,523 | 878 |

`NNJAObsConv` reads NCEP's merged, QC'd PrepBUFR product, which folds
together multiple raw report families (rawinsonde, aircraft, profilers,
etc.) into one high-report-type-fidelity `t` population. `NNJAAIObsConv`
reads only the raw ADPUPA (rawinsonde) dump stream -- the nnja-ai catalog
does not currently publish the merged PrepBUFR product or a GPS-RO dataset.
The ~20x wall-clock speedup is real (no BUFR parsing, no PrepBUFR-scale
message volume), but the ~12x fewer rows reflects reading a narrower raw
data product, not equivalent coverage decoded faster. `NNJAAIObsConv` is a
reasonable option when raw radiosonde temperature/wind/derived-humidity and
raw surface pressure are enough; it is not a full substitute for
`NNJAObsConv`'s merged-PrepBUFR `t`/`u`/`v`/`q`/`pres`/`gps` coverage.
